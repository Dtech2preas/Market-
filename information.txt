# DTECH Student Business Hub - System Architecture & Documentation

## 1. Platform Overview
The DTECH Student Business Hub is a web-based marketplace and directory platform designed specifically for students to list, promote, and manage their small businesses. It functions as a centralized hub where potential customers can discover student-run services and products, while giving student entrepreneurs a professional, customizable online presence.

**Target Audience:**
- **Student Entrepreneurs:** To register, onboard their business details (basic info, contact, branding, listings), preview their dynamic site, and manage it via a dashboard.
- **Customers / General Public:** To browse the marketplace, filter by categories, view dynamic business profiles, and contact businesses (primarily via WhatsApp).
- **Administrators:** To review, approve, request changes, suspend, or manage business applications, as well as handle SEO propagation.

**Key Features:**
- **Dynamic Subdomain/Slug Routing:** Businesses get their own virtual space with clean URLs based on their slugs.
- **Step-by-step Onboarding & Editing:** A 7-step wizard (separated into individual HTML files) for creating and updating a business profile, avoiding complex Single Page Application patterns.
- **Draft & Published State Management:** Edits are saved as drafts and only go live to the public when explicitly published.
- **Admin Workflow:** Status tracking (Draft, Pending Review, Approved, Request Changes, Declined, Verified Student, Featured, Suspended).
- **Marketplace Directory:** A central directory with advanced client-side fuzzy search and filtering to minimize backend reads.

## 2. Architecture & Data Flow
The platform is built using a modern, serverless architecture optimized for high performance and low database read/write costs.

### Tech Stack:
- **Frontend:** Pure HTML, CSS (global `styles.css`), and Vanilla JavaScript. Safe DOM manipulation is strictly used over `innerHTML` to prevent XSS vulnerabilities.
- **Backend:** Cloudflare Workers (`worker.js`) running in a serverless edge environment.
- **Database / Storage:** Cloudflare KV (Key-Value store), utilizing the `MARKET_KV` namespace.
- **Bundler:** ESBuild (`esbuild.mjs`) is used to bundle backend dependencies (`bcryptjs` for password hashing, `jose` for JWTs) into a single `dist/worker.js` distribution.
- **Image Hosting:** ImgBB API (external, proxied securely through the worker via `/api/upload`).
- **CI/CD Deployment:** GitHub Actions automatically deploys changes pushed to the main branch to Cloudflare.

### How It Works (The Data Flow):
1. **Frontend to Backend Communication:** The frontend vanilla JS uses the `fetch()` API to send asynchronous requests to the Cloudflare Worker absolute URL (`https://late-frost-770c.nakiaklocko57.workers.dev`).
2. **Authentication:** User registration hashes passwords using `bcryptjs`. Login generates a JWT using `jose`, which is stored in local storage and sent in the `Authorization: Bearer <token>` header for protected requests.
3. **Drafting (Local vs Cloud):** While going through the onboarding or editing steps, data is temporarily stored in the browser's `localStorage` (prefixed with `onboarding_` or `editor_`). Once the user reaches the end and submits, it is pushed to the backend KV.
4. **Cloudflare KV Storage Strategy:**
   - Users are stored under `user:<id>`. Emails mapped via `email:<email>`.
   - Businesses are stored under `business:<id>`.
   - Business lookups via slug map `slug:<slug>` to `<business_id>`.
   - User-to-Business mappings use `user_business:<user_id>` to `<business_id>`.
   - The marketplace directory uses a lightweight array under the key `marketplace:index` to avoid heavy database scanning.
5. **Dynamic Rendering:** When a request hits a clean route (`/<slug>`), the Cloudflare Worker intercepts it. It retrieves the business data and injects it into a pre-defined HTML template shell generated server-side.

## 3. Data Schema & KV Structures

### User Schema (`user:<id>`)
```json
{
  "id": "user:abc123xyz",
  "email": "student@dtech.co.za",
  "fullName": "John Doe",
  "passwordHash": "$2a$08$...",
  "role": "user",
  "createdAt": 1690000000000
}
```

### Business Schema (`business:<id>`)
The business record separates draft and published data to support offline edits.
```json
{
  "id": "business:xyz987",
  "userId": "user:abc123xyz",
  "slug": "johns-tech-repair",
  "status": "approved", // draft, pending_review, approved, request_changes, declined, verified, featured, suspended
  "seoPropagated": true, // Flag indicating if static HTML file exists in /profile/
  "draftVersion": {
    "basic": { "businessName": "Johns Tech", "category": "Technology", "province": "Gauteng", "description": "...", "tagline": "..." },
    "contact": { "email": "...", "phone": "...", "whatsapp": "...", "address": "...", "instagram": "..." },
    "branding": { "logo": "https://imgbb.com/...", "cover": "https://imgbb.com/...", "gallery": ["url1", "url2"] },
    "listings": [{ "id": "list_1", "title": "Screen Repair", "price": "R500", "description": "..." }],
    "sections": { "hero": true, "about": true, "gallery": true, "listings": true },
    "cta": { "type": "whatsapp", "text": "Message Us", "value": "27812345678" }
  },
  "publishedVersion": { ... identical structure to draftVersion when published ... },
  "createdAt": 1690000000000,
  "updatedAt": 1690000000000
}
```

### Marketplace Index (`marketplace:index`)
A lightweight array for rendering the homepage quickly.
```json
[
  {
    "id": "business:xyz987",
    "slug": "johns-tech-repair",
    "name": "Johns Tech",
    "category": "Technology",

    "logo": "https://imgbb.com/...",

    "status": "approved",

  }
]
```

## 4. API Requests and Endpoints

All backend logic is handled inside `worker.js` via the `fetch` event listener. CORS headers are strictly applied to all responses to allow frontend cross-origin requests.

### Subdomain/Slug Routing & Rendering (SSR)
- **Method:** `GET`
- **Path:** `/<slug>`
- **Explanation:** The worker treats non-standard paths as slugs. It looks up `slug:<slug>` in KV. It fetches the business JSON, escapes all user input to prevent Stored XSS, and dynamically interpolates it into a massive HTML shell generated server-side.

### Authentication API
- **`POST /api/auth/register`**: Hashes passwords using `bcryptjs` and stores user mapping.
- **`POST /api/auth/login`**: Verifies credentials and returns a signed JWT using `jose`.
- **`GET /api/auth/me`**: Requires JWT. Returns authenticated user details.

### Marketplace API (Public)
- **`GET /api/marketplace`**: Returns the `marketplace:index` from KV, filtering for businesses with `published`, `approved`, or `verified` statuses.
- **`GET /api/business/[slug]`**: Returns full JSON for a specific business (used when routing bypasses SSR).
- **`GET /sitemap.xml`**: Dynamically generates an XML sitemap of all published businesses with clean URLs for search engine indexing.

### Dashboard & Business Management API (Protected)
- **`GET /api/dashboard/my-business`**: Uses the JWT to find the user's ID, looks up `user_business:<userId>`, and returns their specific business data.
- **`POST /api/dashboard/business`**: Accepts massive JSON payloads containing `basic`, `contact`, `branding`, `listings`, `sections`, and `cta` data. Saves to `draftVersion`.
- **`POST /api/dashboard/publish`**: Copies the `draftVersion` over to the `publishedVersion` and updates `marketplace:index`.
- **`POST /api/upload`**: Accepts `multipart/form-data` with an image. Proxies the image securely to ImgBB to protect the API key from the frontend.

### Admin API (Protected)
- **`GET /admin/businesses`**: Scans KV for all `business:` keys for admin review.
- **`POST /admin/action`**: Modifies business status (`approve`, `decline`, etc.). Auto-publishes on first approval.
- **`POST /admin/seo-mark-propagated`**: Updates the `seoPropagated` flag to `true` for a given business once an admin has manually generated and uploaded the static HTML file for OpenGraph preview support.

## 5. Detailed File Breakdown

### Root Configuration & Deployment Files
- **`package.json` / `package-lock.json`**: NPM configurations for `bcryptjs` and `jose`.
- **`esbuild.mjs`**: Custom build script to bundle backend files into `dist/worker.js`.
- **`wrangler.toml`**: Cloudflare configuration (entry point, KV bindings).
- **`.github/workflows/deploy.yml`**: Automates deployment using `cloudflare/wrangler-action@v3`. Crucially passes environment variables like `IMGBB_API_KEY` into the runner so they aren't lost.

### Core Backend logic
- **`worker.js`**: Contains ALL backend routing, JSON parsing, API endpoints, ImgBB proxying, authentication, and SSR Server-Side HTML generation. Includes HTML escaping utilities.

### Global Assets & Frontend
- **`styles.css`**: Centralized CSS. Defines the dark blue aesthetic, variables (`--primary`, `--bg`), pill-style buttons, and responsive grid layouts.
- **`index.html`**: The main public landing page. Features a client-side search and filtering system using an in-memory `allBusinesses` array to drastically reduce backend database queries.
- **`login.html` & `register.html`**: Authentication screens. Account creation is kept strictly separate from business onboarding.
- **`dashboard.html`**: Central hub for logged-in students. Features a client-side "Profile Completeness Score" calculation that dynamically inspects business data properties and outputs actionable UI tips without storing the score in the database.

### The Onboarding & Editor Flows
Separated strictly into distinct HTML files, avoiding SPA anti-patterns.
- **`onboarding-1-basic.html` to `onboarding-7-preview.html`**: Creation wizard using `localStorage` (`onboarding_` prefix).
- **`editor-1-basic.html` to `editor-7-preview.html`**: Editing wizard using `localStorage` (`editor_` prefix), loading from `draftVersion`.
- **`onboarding-preview-desktop.html` / `mobile.html`**: Synchronized preview IFrames.

### Dynamic Rendering & Routing Fallbacks
- **`business-dynamic.html`**: Fallback structure reference.
- **`business-profile.html`**: A secondary standalone viewing page accessed via `?slug=...` instead of a route. Used specifically when `seoPropagated` is `false`.

### The Admin System
- **`admin.html`**, **`admin-pending.html`**, **`admin-review.html`**, **`admin-approved.html`**: Status management dashboards.
- **`admin-sidebar.html`**: Navigation (manually synchronized across admin pages).
- **`admin-seo.html`**: Critical utility page. Generates static HTML blocks injected with OpenGraph tags (for WhatsApp link previews) which admins then download, commit to the `/profile/<slug>.html` directory, and mark as propagated in KV.

## 6. What's New (Added Aug 2, 2026)
*This section highlights architecture details, custom logic, and features that were completely missing from earlier documentation iterations.*

- **Client-Side Profile Completeness Score (`dashboard.html`):** The dashboard now dynamically calculates a completeness percentage (0-100%) purely on the frontend by analyzing the fetched business JSON payload. It displays missing fields (e.g., "Upload a logo") without needing backend storage for the score.
- **SEO Propagation & OpenGraph Workflow (`admin-seo.html`):** Because Cloudflare Workers on GitHub Pages cannot intercept custom domain previews perfectly on all platforms, a manual admin workflow was added. Admins generate static HTML files containing meta tags for a business, upload them to a `/profile/` folder, and flip a `seoPropagated` boolean flag in the KV database.
- **Dynamic Routing Fallback (`index.html` & `dashboard.html`):** The frontend strictly checks the `seoPropagated` flag. If true, it routes clicks to `/profile/<slug>.html`. If false, it falls back to the query parameter route (`/business-profile.html?<slug>`).
- **Secure Image Upload Proxy (`/api/upload` in `worker.js`):** The ImgBB API key is no longer dangerously exposed in the frontend HTML. The worker now features a secure multipart proxy endpoint that handles the upload server-side and returns the secure URL string.
- **Client-Side Marketplace Search Filtering (`index.html`):** The marketplace now fetches the `marketplace:index` array once into memory (`allBusinesses`). All category and text-based fuzzy searching is performed using JavaScript array filtering on the client, minimizing KV reads and improving UI responsiveness.
- **XML Sitemap Generation (`/sitemap.xml` in `worker.js`):** The worker dynamically generates a search-engine compliant `sitemap.xml` mapping clean URLs for all published businesses.
- **Automated Deployment & Secrets (`.github/`):** The repository utilizes GitHub Actions for continuous deployment. Specific fixes like `ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION` and explicit secrets passing (`IMGBB_API_KEY`) were implemented to resolve Wrangler v3 edge cases.
- **Strict Server-Side HTML Escaping:** Template literal escaping is heavily enforced inside `worker.js` via an `escapeHTML()` helper to protect against Stored Cross-Site Scripting (XSS) when rendering user-submitted business profiles.
